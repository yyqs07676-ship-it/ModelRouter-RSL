# RSL 设计说明

## 1. 问题定义

ModelRouter 原本是「静态策略路由器」：由 profile、关键词、语义分类和 cascade 决定模型。
本作业要把它变成「会学习的路由器」：同一类任务重复出现时，系统应逐渐把请求交给历史表现更好的模型。

## 2. 两个学习循环

### 2.1 轮内递归（递归修订）

```
第 1 轮：question → model → answer₁ → judge(answer₁) → score₁
        若 score₁ < threshold：
第 2 轮：question + answer₁ + critique → model → answer₂ → judge(answer₂)
        保留得分最高的答案
```

递归的含义：上一轮的输出和评价作为下一轮输入，而不是独立重采样。

### 2.2 跨请求学习（策略更新）

每个任务类型维护一张 Q 表：

```
Q[task_type][routing_key]
```

结束后按奖励更新：

```
reward = quality − λ·normalized_latency
Q ← Q + α(reward − Q)
```

下次同类型任务按 Q 值选择模型，并以 ε 的概率探索其他模型。

## 3. 质量信号

| 任务 | 评估方式 | 原因 |
| --- | --- | --- |
| 最大公约数 | `math.gcd` | 可精确判定 |
| 加法 / 乘法 | Python 计算 | 可精确判定 |
| 开放问答 / 写作 | LLM 裁判 | 无唯一答案 |

LLM 裁判的提示词要求先核对正确性，并规定「存在事实或计算错误时 score ≤ 3」。
若输出无法解析，会追加一次「只输出 0–10 数字」的重试；仍失败则记中性分 5，避免把解析失败当成答案质量差。

## 4. 冷启动与评估公平性

- 冷启动：所有 Q = 0.5，按候选顺序选择第一个（成本优先，选小模型）。
- 学习阶段：固定随机种子打乱训练集，避免「先难后易」造成采样顺序偏差。
- 评估阶段：`explore=false, learn=false`，冻结策略，避免评估请求本身修改 Q 表。

## 5. 持久化

`rsl_policy` 与 `rsl_events` 两张表存放在 ModelRouter 的 SQLite 中。
所有写操作显式 `commit`，否则重启后学习结果会丢失（本项目实际踩过这个坑）。

## 6. 关键失败案例（真实记录）

1. **LLM 裁判误判**：1.5B 裁判给「48 和 18 的最大公约数 = 3」打 7 分。→ 引入确定性校验器。
2. **结论数字提取错误**：正则把「63 加 29 等于 92」里的 63 当成结论。→ 改为优先匹配 `等于/=/结果是` 的最后一次出现。
3. **训练集顺序偏差**：前 10 题全是 GCD（难），后 14 题是加减乘（易），小模型在后期刷高分，Q 值虚高。→ 固定种子打乱 + 2 轮训练。
4. **评估污染策略**：评估请求结束后仍更新 Q，导致同一组评估中途换模型。→ 增加 `learn=false`。
5. **未提交事务**：服务内存里 Q=0.93，磁盘上仍是 0.5。→ 写路径显式 commit。

## 7. 可扩展方向

- 更细粒度奖励（0–100 连续分）
- 上下文老虎机（LinUCB / Thompson Sampling）替代 ε-greedy
- 接入代码执行器、单元测试作为 reward
- 多任务类别并行学习与 profile 级隔离
